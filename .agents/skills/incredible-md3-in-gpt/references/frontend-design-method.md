# Frontend design method: intentional direction, critique, and restraint

This guide adapts useful workflow ideas from Anthropic's [Frontend Design skill](https://github.com/anthropics/skills/tree/main/skills/frontend-design) to native mobile product design. It is an original synthesis, not a copy or bundled version of that skill.

The goal is a product-specific visual identity rather than a familiar AI-generated template.

## 1. Ground the design in the product

Before selecting colors or components, identify:
- The product's actual subject matter and domain.
- The people using it and their context.
- The primary job the interface must make easy.
- The information that is characteristic of this product.
- The emotional quality appropriate to the product: calm, precise, playful, clinical, energetic, or another justified direction.

Let the domain inform the visual language. A neural-signal workstation, a reading app, a travel planner, and a children's creative tool should not receive the same palette, density, typography, and motion.

If the brief leaves important context unknown, make a concrete proposal and validate it before committing to a product-wide design.

## 2. Produce a compact design plan before writing UI code

For a new app or product-wide redesign, write a short plan containing:

### Color
- Name 4–6 brand anchor colors with hex values.
- Explain the role of each anchor color.
- Map them into semantic roles and light/dark schemes.
- Keep semantic status colors distinct from brand decoration.

The 4–6 colors are a planning aid, not a limit on the tonal roles generated by Material or the platform.

### Typography
- Choose one primary type family, or two clearly differentiated families when the product needs them.
- Define roles for screen titles, section titles, body, controls, labels, and numeric data.
- Specify weight, size, and line-height intent.
- Avoid choosing a fashionable typeface without a product-specific reason.

### Layout
- Describe the screen structure in plain language.
- Use a compact ASCII wireframe when it clarifies hierarchy or alignment.
- State whether content is left-aligned, centered, edge-aligned, or arranged in another deliberate way.
- Identify the primary focal point, primary action, and supporting information.
- Explain the density choice using the real amount and frequency of content.

### Shape, surfaces, and motion
- Define a small shape vocabulary and surface hierarchy.
- State where M3 Expressive shapes or components add useful emphasis.
- Describe the motion that communicates navigation or state change.
- Explicitly name effects that will not be used.

### Design principles
- State the one-sentence visual thesis.
- Name the one distinctive visual decision that gives the product character.
- State which Apple design principles are most relevant to the product.
- State how minimalism will reduce noise without hiding functionality.

## 3. Critique the plan before implementation

Review every major choice against the actual brief. Ask:
- Could this same plan be produced for almost any app in this category? If so, what makes it specific to this product?
- Is the palette a deliberate product choice or a familiar default?
- Is the typography chosen for the content and brand, or merely because it looks fashionable?
- Is the layout appropriate to the task, or a generic card grid?
- Is the expressive treatment doing useful work?
- Does the screen have one clear focal point?
- Can any decoration, label, container, animation, or line be removed without reducing clarity?

Check for common generated-design defaults. Do not use these automatically:
- Warm cream backgrounds paired with a high-contrast serif and terracotta accent.
- Near-black backgrounds with a single neon accent.
- Newspaper-like grids, hairline rules, and dense columns when the content is not editorial.
- Identical rounded cards for every content group.
- Decorative gradient washes, glow, blur, or shadows.
- Tracked uppercase eyebrow labels above ordinary headings.
- Metadata joined with decorative separators.
- Monospace labels used only to make an interface look technical.
- Arrows appended to every link or button.
- Repeated fade-and-slide entrances for every section.

These treatments are valid when the brief calls for them. The rule is to make a conscious, product-specific choice rather than accepting a default.

Only start implementation after the plan has a clear reason for its palette, typography, layout, shape, and motion.

## 4. Spend visual emphasis deliberately

- Let one element or moment carry the strongest visual expression.
- Keep the rest of the screen quiet enough to support it.
- Prefer one meaningful M3 Expressive treatment over many competing effects.
- Remove one decorative element during the final critique.
- Do not add a hero banner to a native utility screen merely because a web landing page would have one.

This is compatible with minimalism: a product can have a distinctive visual signature while keeping most of its interface calm and functional.

## 5. Treat words and motion as part of the design

- Write from the user's perspective, not from internal system architecture.
- Use plain language, sentence case, and active verbs.
- Name an action by its result: the same action should use the same verb in the control and its completion feedback.
- Give each visible string one job.
- Make errors specific and actionable; make empty states point to a useful next step.
- Keep explanatory copy only when it changes a decision, enables safe action, or resolves a real information gap.
- Use non-interactive motion sparingly. Motion caused by user action should explain what changed and remain responsive.

Read [copy-discipline.md](copy-discipline.md) for the visible-copy rules.

## 6. Build, inspect, critique, and refine

1. Implement the approved visual plan with shared semantic tokens.
2. Run the app and capture representative screenshots when the environment supports it.
3. Inspect actual device-sized output, not only source code or a desktop mockup.
4. Compare the result against the visual thesis and the original product tasks.
5. Fix hierarchy, alignment, density, typography, contrast, and platform behavior before decorative details.
6. Remove unnecessary decoration and redundant copy.
7. Capture screenshots again after changes.
8. Report what was run and visually verified.

Do not claim visual verification when only static code was reviewed.
